Wise Mentoring Ship

A cross-university mentorship platform — built at an agency, then handed to me to keep.

Role
Software Engineer Intern, Skooldio (Feb – Jul 2026) → Software Engineer (Part-time), Wise (Aug 2026 – present)
Scale
1,000+ mentors and mentees across Thai universities
Team
Co-developed features alongside the engineering manager

Universities had no shared way to pair students with mentors: matching happened in spreadsheets and chat groups, and nobody could see the state of a request once it left the room. Wise Mentoring Ship turns that into one platform — mentees browse and request, mentors accept or decline, and administrators can see and correct the whole pipeline.

What I built

  • The registration flow, the mentee-request and mentor-handling logic, the dashboard, the homepage, the paginated explore pages, and the admin back-office flow — front end through to API, on top of the base design tokens and reusable components I set up for the rest of the UI.
  • A data-migration plan and the scripts behind it, to move records already in use into the new schema without losing or duplicating a relationship.
  • The CI/CD pipeline, and the LINE integration — Official Account, Flex messages and the Developer APIs — with GCP Cloud Tasks driving scheduled and asynchronous notifications.

How it was built

Clean architecture, not just clean files

DTOs, Entities and Use Cases kept apart, so a change to the transport layer never reaches into domain logic. Swagger docs generated from the same definitions the API validates against.

Notifications that survive a slow request

Scheduled and fan-out LINE messages run through GCP Cloud Tasks rather than inside the request that triggered them, so a slow push never becomes a failed user action.

Still mine

When the Skooldio engagement ended in July, Wise retained me directly to keep owning the backend of what we had built — shipping API and back-office features, resolving production issues against a live user base, and extending into the React front end when a change spans the stack.

RAG GIS API

Turning GIS impact analyses into Thai environmental reports — for a government agency that retries on failure.

Role
Contributor — the /analysis endpoint end to end, plus SSE streaming for the chat API
Client
ONEP — Office of Natural Resources and Environmental Policy and Planning
Source
github.com/dannifyz/rag-gis-api

Before a project breaks ground, ONEP runs a spatial analysis: which protected natural sites, cultural sites and conservation zones fall inside the legal radius, how close, how much overlap. The output is structured data. What the agency actually needs is a Thai narrative report that reads those numbers back with the right regulation cited beside them — work that used to be done by hand. This API does it.

The decisions I would defend in review

Numbers cannot be allowed to drift

Every count, category breakdown and legal citation is assembled in code before the model is called. The model is handed that finished skeleton and asked only for a closing synthesis paragraph — so there is no figure in the report a hallucination could move.

Fail the way the caller expects

ONEP retries on 5xx, 429 and timeout, but treats 4xx as permanent rejection. So an empty model response raises rather than returning 200 with a half-written report, and the endpoint budgets 100s inside their 120s disconnect window — a hang becomes a clean retry, not a dropped request.

Forward-compatible on purpose

Unknown fields are ignored and an unrecognised schema_version is logged and processed rather than rejected: a future version of their payload still carries every field we read, and refusing it would break a live integration over a version string.

Retrieval grounded in this project

The RAG query is built from the project type plus only the site categories with a non-zero count, so retrieval is not steered toward law about sites this project never touches.

Also contributed: SSE token streaming for the chat API, so answers render as they are generated rather than after the full response completes, with source listing for the chunks behind each answer.

Tax Tracker

Capital-gains tax for Thai investors, computed from broker PDFs that never leave the browser.

Role
Sole author
Why
Built for my own filing, after doing a year of it by hand in a spreadsheet
Source
github.com/miramsalp/tax-tracker

Thai investors holding foreign equities have to report realised capital gains, and their broker gives them confirmation notes as PDFs — one per trade, no export. Reconstructing FIFO cost basis across a year of those by hand is slow and easy to get wrong. Drop the PDFs into the page and it does the accounting.

The decisions I would defend in review

Refuse rather than guess

The parser reads its broker's layout by character position, and rejects a document it does not recognise instead of inferring structure. A wrong number here goes onto a tax return — a confident guess is worse than a refusal.

The data has nowhere to go

No server, no database, no upload. Parsing runs entirely in the browser and the Content Security Policy is locked to connect-src 'self', so a complete trade history cannot be exfiltrated even by a dependency that wanted to.

Check the arithmetic against a second source

Confirmation notes are cross-checked against monthly statements, so a missing or duplicated trade surfaces as a discrepancy rather than quietly shifting every FIFO lot after it.

Say what it cannot do

Corporate actions — splits and stock dividends — break FIFO cost basis, so the tool warns rather than reporting a clean number it has no basis for. Documented limits, not hidden ones.
